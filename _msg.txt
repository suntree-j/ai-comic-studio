## docs/modifying.md（后续怎么改）
回答「这个项目以后怎么动」，八个部分：

1. **改动地图** —— 想改什么就改哪个文件；并区分「改数据」vs「改代码」，
   能用 JSON 表达的就不改代码
2. **七个常见改动**（照着做即可）
   - 换内容/改台词：不用改代码，工作台点几下或改 dialogue.json
   - 加校验规则：validator.py 的写法 + 必须同时做的三件事
   - 加生图服务商：providers.py 的完整模板 + 必须同时做的四件事
   - 改画风/加角色：改 bible.json 的四条硬规矩
   - 改提示词：三段式结构 + 两条底线
   - 改界面：三个文件 + 每次必跑 node --check
   - 加接口：四条纪律（只写 IR / 不提供改页码接口 / 清缓存 / 加测试）
3. **五条红线**（破一条就退回原来的坑）
   - 不要重排页码（上次项目因此整个放弃修正）
   - 不要把对白写进生图提示词（上次 216 格全被画上文字）
   - 不要让程序猜说话人
   - 不要在提示词里改写角色外观
   - 不要让中文字体静默降级（接口全绿但全是方块）
4. **改动后的标准流程** + 「改了什么就要额外跑什么」对照表
5. **部署相关**：更新线上的命令、服务器关键路径、运维命令、回滚方式，
   以及「这台机器有别人生产系统」的注意事项
6. **想加新功能时的建议顺序**（按价值/成本排序，建议先做真实生图案例与在线试玩）
7. **面试可能被追问的 8 个点**及回答要点
8. 最短路径速查

## tests/test_docs.py（12 个测试，166 passed）
★ 文档最容易骗人的地方是**示例代码里的符号名和真实代码对不上** ——
照着抄会 AttributeError，比没文档更糟。所以把指南里引用的每个符号
都实际 import 一遍核对：
- validator / providers / prompt / page / api 的关键符号与函数签名
- 指南引用的脚本、路径、文档是否真实存在
- 五条红线必须都写在指南里
- README 必须链接到指南
- 所有文档之间的内部链接不能失效
- 文档里 `python scripts/x.py` 的写法必须有效（脚本存在 + 有 __main__ 入口）
