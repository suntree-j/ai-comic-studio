# 实战复盘：五个结构性坑

> 本项目源于一次真实产出：**《全职法师》2426–2445 章改编，20 章 / 168 页 / 216 格**。
> 那次用散落脚本 + 人工校验完成，踩了五个坑。
> **本项目的 12 条规则与全部架构设计，都是这些坑的解法。**

这不是「事后总结」，而是「设计输入」。

---

## 坑 ①：对白烧进了图片

### 现象

为了让分镜提示词「更准确」，我把小说原文（含 `「」`）直接写进了生图提示词。
结果模型**把台词画在了图上**。之后系统又叠了一层气泡 → **同一句话出现两次**。

### 代价

- 全篇 216 格必须逐格排查重复对白
- 改任何一句话都要**重新出图**（约 90 秒/格）
- 改 20 句 = 改 20 页 × 每页 90 秒 ≈ 半小时，且不保证一次成功

### 根因

**把「内容」和「呈现」混在了一层。**
对白是结构化数据，不该进像素。

### 解法（本项目的设计）

```
① 提示词里加硬约束：绝对不要出现任何文字
   bible.style.no_text_rule 会逐字拼进每一格

② 对白独立成层：dialogue.json
   渲染时才把气泡叠加到单格图上

③ 收益
   改一句话 → 重渲染那一页（3 秒），不碰生图
```

**对应代码**：
- `packages/render/prompt.py` → `RULE_NO_TEXT`
- `packages/render/page.py` → `_render_bubbles()` 在合成阶段叠加
- `packages/ir/models.py` → `DialogueBook` 与 `Storyboard` 完全分离

## 坑 ②：页码中途变动

### 现象

用户说「第 77 页这句不对」。
我删掉了第 77 页（那一格不要了）→ **后面的页码全部前移**。
于是用户看到的「第 77 页」和我本地的「第 77 页」**不再是同一页**。

### 代价

连续 **3 轮沟通都无法对齐页码**，最后不得不放弃修正。

这是整个项目里最贵的一次失误 —— 不是技术难度，而是**数据模型缺陷导致的协作崩溃**。

### 根因

页码是**位置**，不是**身份**。
删一格就让所有后续页码失效，等于把「身份」绑在了「位置」上。

### 解法（本项目的设计）

```jsonc
// layout.json —— 页码一经分配即冻结
{ "page": 77, "type": "empty", "note": "原 ch2436_P005，已删除，留空" }
```

**规则**：
1. 分镜全部出图后，**一次性排定页序**
2. 删除某格 → 该页标 `empty`，**页码留给空位，不重排**
3. 新格插入 → 占用已有空位，或序号往后追加

**三重保障**：
- 数据层：`Layout._pages_consistent()` 强制页码连续且唯一
- 规则层：`IR-009/010` 校验引用合法性与无漏排
- 接口层：工作台 API **刻意不提供改页码的接口**

**对应代码**：
- `packages/ir/models.py` → `Layout` / `LayoutPage`
- `packages/ir/validator.py` → `_rule_layout_consistency`
- `apps/api/server.py` → 没有 PATCH page 接口

## 坑 ③：四层索引互相打架

### 现象

为了灵活，索引被拆成了四层：

```
分镜表（格子定义）
  → 混合素材映射（新版/旧版素材混合）
    → 显式映射（人工指定某格用哪张图）
      → 素材库（实际文件）
```

**任何一层不同步，就会出错图**，而且很难定位是哪一层错了。

### 代价

多次出现「这张图不该在这里」的问题，排查要翻四个 JSON。
更糟的是：删一格后，**图像与镜头整体错位一格**，
导致「删了却还在」「图不对文」的诡异现象。

### 根因

**间接层过多 = 状态空间爆炸。**
每一层都是一个可能不一致的真相来源。

### 解法（本项目的设计）

收敛为**两张表 + 单一数据源**：

```
bible.json       角色/场景/技能/风格（一致性的唯一来源）
storyboard.json  每格画什么（引用 bible 的 id）
dialogue.json    谁说哪句、气泡放哪
layout.json      页序（冻结）
```

**关键**：`cast` 里**只写角色 id，绝不内联外观**。
外观从 bible 取 → 不可能出现「这格换了衣服」，
因为**根本没有第二个地方能定义外观**。

**对应代码**：
- `packages/ir/models.py` → `CastMember` 只有一个 `id` 字段
- `packages/render/prompt.py` → `render_character_block()` 从 bible 取标准块

## 坑 ④：改动只在图里，项目一删全没

### 现象

对白、技能名、气泡位置都**烧进了成品图**。
后来项目要清理，删掉目录后 —— **全部对白数据永久丢失**。

再想改一句台词，只能从图片里人肉抄回来。

### 代价

- 无法版本管理（改了什么看不见）
- 无法协作（只能整张图替换）
- 无法迁移（换工具就要重做）

### 根因

**把「数据」和「产物」混为一谈。**
成品图是**产物**，随时可由数据重生；不该作为真相来源。

### 解法（本项目的设计）

```
数据层（人工编辑的唯一入口）
  bible.json / storyboard.json / dialogue.json / layout.json

产物层（随时可重生）
  assets/panels/*.png    单格底图
  out/comic.pdf          成品
```

**原则**：
1. **所有人工编辑只改 IR**（工作台就是这么做的：拖气泡 → PATCH JSON）
2. 产物可以随时全删，一条命令重建
3. 成品图**永不手改**；确需手改必须标记 `manual: true` 让程序跳过

**对应代码**：
- `packages/render/studio.py` → `render()` 可从 IR + 素材完整重建
- `apps/api/server.py` → 所有 PATCH 都写回 JSON，不碰图片

## 坑 ⑤：没有阶段自检，一口气跑完才发现错

### 现象

流程是：写分镜 → 出图 → 抽对白 → 装配 → 导出。
因为每次出图很慢，习惯了「一次跑完再看结果」。

结果：**出到第 100 格才发现前面 30 格的角色服装全错了**。

### 代价

- 返工量 = 已完成量
- 而且不知道从哪一步开始补救（是分镜错了？还是提示词错了？）

### 根因

**没有检查点，错误会一路传播并被放大。**

### 解法（本项目的设计）

**12 条业务规则 + 阶段化自检。**

每完成一个阶段就先校验，不通过不往下走：

```
① 分镜生成   → 校验 IR-001/002/003/004/012（引用、距离、表情、损伤、景别）
② 对白抽取   → 校验 IR-006/007/011（说话人、可追溯、是否在场）
③ 排版       → 校验 IR-009/010（页序自洽、无漏排）
④ 气泡布局   → 校验 IR-008（坐标合法）
```

更关键的是：**校验失败不是报错终止，而是回喂给 LLM 自修复**。

```python
for attempt in range(MAX_REPAIR):
    ir = llm.generate(prompt, schema=ComicIR)
    errors = validate(ir, bible)
    if not errors:
        return ir
    prompt = repair_prompt(original=prompt, bad_output=ir, errors=errors)
# 仍失败 → 标记 pending_human，交人工，不硬渲染
```

**对应代码**：
- `packages/ir/validator.py` → 12 条规则
- `packages/agent/skills.py` → `repair_until_valid()`

## 坑之外：几个花了时间才发现的小问题

| 问题 | 根因 | 解法 |
|---|---|---|
| 敌对双方画得像聊天 | 提示词没写距离，模型默认画近 | **IR-002**：两人以上同框强制写具体距离 |
| 主角全程一个表情 | 提示词没逐格指定表情 | **IR-003**：相邻两格不得同表情 |
| 长了翅膀的角色看起来是另一个人 | 变身形态跟常态脸型瞳色不一致 | 硬规则：**变体必须 preserve_face + preserve_eye_color** |
| 大场面没有体量感 | 人物画太大 | **极远景硬规则**：人物占画面高度 ≤1/10 |
| 伤口自愈 | 没有跨格状态追踪 | bible 里 `Injury` 带 `since` / `healed_at`，**IR-004/005** 校验 |
| 气泡压在人物脸上 | 不知道画面哪里空 | **内容能量最小化** + 人物左右检测（排除雪白背景） |
| 气泡与箭头指向错人 | 靠程序猜说话人在哪侧 | 侧向判定给「建议」，**必须人工确认并锁定** |
| 生图 API 报 HTTP 400 | `response_format` 写成了 `png` | 必须写 `url`，格式放 `output_format` |
| 批量出图大量失败 | 并行多进程被限流 | 单进程串行 + 额度超限单独抛异常 |

## 一句话总结

> **数据与人分离，页码定死不回头，每步都要自检。**
> 这三条能避免 90% 的返工。

展开成十二条：

| # | 铁律 |
|---|---|
| 1 | 提示词里绝不能有台词文字 |
| 2 | 对白与画面分离，改字不重出图 |
| 3 | 页码一经分配永久冻结 |
| 4 | 所有人工编辑只改 JSON |
| 5 | 每一句对白都要人工确认说话人 |
| 6 | 气泡位置一旦指定就锁定 |
| 7 | 每阶段先自检再进下一步 |
| 8 | 参考图只管脸型气质，服装发色以文字为准 |
| 9 | 同一角色全篇只能有一套衣服 |
| 10 | 敌对双方同框必须写明距离 |
| 11 | 大场面敢把人物画小 |
| 12 | 一切改动先备份，备份与工作目录分离 |

## 这些坑怎么变成了代码

| 坑 | 变成了 |
|---|---|
| ① 对白烧进图 | `DialogueBook` 独立 + `RULE_NO_TEXT` + 分层渲染 |
| ② 页码变动 | `layout.json` 冻结机制 + `IR-009/010` + API 不提供改页码 |
| ③ 四层索引 | 收敛为四文件 + `CastMember` 只存 id |
| ④ 改动只在图里 | 「数据层 / 产物层」分离 + 工作台只改 IR |
| ⑤ 无阶段自检 | 12 条规则 + `repair_until_valid()` 自修复循环 |

**这就是本项目与「一次性脚本」的区别：从真实失败中提炼出可复用的约束。**
